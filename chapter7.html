Chapter 7 · Algorithm Design & Problem Solving

This chapter is about turning a messy real-world problem into a clean, testable algorithm: Analyse → Design → Code → Test. You'll use decomposition and abstraction to break problems down, flowcharts and pseudocode to design solutions, five standard algorithms as reusable building blocks, and validation/verification/test data/trace tables to prove your algorithm actually works.

7.1–7.2 Designing a solution

life cycle, abstraction, decomposition
Program development life cycle
Always in this order — and testing often sends you back to an earlier stage.

7.1 Program Development Life Cycle

Every program is built in four stages, always in this order:

ANALYSE → DESIGN → CODE → TEST
StageWhat happens
AnalyseUnderstand and break the problem down — what is it really asking?
DesignPlan the solution using structure diagrams, flowcharts or pseudocode — before any code is written.
CodeWrite the program in a programming language, following the design.
TestRun the program with test data to find and fix errors.
⚠️ Common Mistake.

Students most often skip Analyse/Design and jump straight to Code. Result: bugs, poor structure, or a program that solves the wrong problem entirely.

💡 Key Term — Abstraction.

Keeping only the details needed to solve the problem, and discarding the rest.

7.2 Abstraction vs Decomposition

AbstractionDecomposition
What it doesKeeps what matters, removes the restBreaks a big problem into small sub-problems
ExampleA subway map shows only stations and lines — not real road shapes or building heights"Get dressed" → select items → remove clothes being worn → put items on in order
💡 Exam Tip.

Each decomposed sub-part can be broken down again until it's simple enough to solve — this repeated breakdown is called stepwise refinement.

7.2 Systems & Sub-systems

Any computer system breaks into four parts:

PartMeaningAlarm clock example
InputData entered while activeSet/cancel the alarm, snooze
ProcessTasks using input + stored dataCheck time vs. alarm time
OutputInformation shown to usersSound/tune when time matches
StorageData saved for laterThe alarm time(s) that were set
📘 Design Tool 1 — Structure Diagrams

Show top-down design: how a system splits into sub-systems hierarchically. Each level is a more detailed breakdown, and any sub-system can be split further if it's still too complex.

7.2 Flowcharts & pseudocode

design tools
Flowchart symbols in action
Oval = start/end · parallelogram = input/output · rectangle = process · diamond = decision.

7.2 Flowcharts (Design Tool 2)

Flow lines are arrows, usually top-to-bottom / left-to-right. A decision box (diamond) must always have its two exits both labelled — yes/no or true/false.

⚠️ Spot the Error.

A decision diamond with only one arrow leaving it is broken — a decision always has two possible outcomes, so one result would have no defined path and the flowchart cannot handle that case.

📘 Worked Example

Rule: $20/ticket. Buy 10+ → 10% off. Buy 20+ → 20% off. Max 25 tickets. For N = 15: Cost = 15 × 20 × 0.9 = $270.

The input check must be N ≥ 1 AND N < 26 — using only one of those conditions would let invalid values (0, negative, or over 25) slip through.

7.2 Pseudocode Rules (Design Tool 3)

  • Keywords in CAPITALS: INPUT, OUTPUT, IF, FOR …
  • Data (variable) names start with a Capital letter: StudentMark
  • Selection/loop bodies indented by two spaces
  • Assignment uses the ← arrow, never =
Operators: + add − subtract * multiply / divide ^ power ( ) group
⚠️ Trick Question.

Amount ← 100 then TotalPrice ← Amount * 3.5 then Discount ← 0.2 then FinalPrice ← TotalPrice − TotalPrice * Discount.
TotalPrice = 350, so FinalPrice = 350 − 70 = 280 (not 100 − 0.2!).

7.2–7.3 Selection, loops & reading algorithms

selection and iteration
The three loops

7.2 Selection: IF vs CASE

IF … THEN … ELSE … ENDIFCASE OF … OTHERWISE … ENDCASE
Best forA condition that is true or false, or a rangeChoosing between several fixed values
Example useGrading by score range (A/B/C by ranges)Matching an exact grade letter already stored

A nested IF is an IF inside another IF; the inner IF only runs if the outer condition was met. Every IF needs its own ENDIF.

📘 Nested IF Walkthrough

Validate PercentageMark (0–100 range check) first, then test Pass/Fail (> 49) only if it passed validation.

PercentageMark = 105 → "Invalid Mark" (fails the range check first). PercentageMark = 49 → "Fail" (49 is not greater than 49).

7.2 Iteration: Three Loops

LoopTypeRuns body …
FOR … TO … NEXTCount-controlledAn exact known number of times
REPEAT … UNTILPost-conditionAt least once (test is AFTER the body)
WHILE … DO … ENDWHILEPre-conditionPossibly zero times (test is BEFORE the body)
💡 Exam Tip — Password Loop.

Asking a user to re-enter a password until it's correct needs REPEAT…UNTIL — you must ask for input at least once before there's anything to test.

⚠️ Spot the Error.

REPEAT and WHILE need their counter initialised and updated manually — miss a step and you get an infinite loop or an off-by-one error. FOR manages its counter automatically.

7.3 Reading Algorithms

To explain what an algorithm does, always answer two things:

  • Purpose — what problem does it solve overall? (e.g. "finds which of two numbers is larger")
  • Processes — what individual steps does it perform? (input two numbers, compare them, print the larger)
💡 Why Exam Questions Use A, B, C….

Single-letter variable names remove clues — you have to work out the algorithm's purpose from its logic, not guess it from a meaningful variable name.

7.4 Standard algorithms

five standard algorithms

7.4 Five Standard Algorithms

AlgorithmHow it works
TotallingRunning sum: Total ← 0 before the loop, then Total ← Total + value each pass
CountingRunning count of how many times something happens, also initialised to 0
Maximum/Minimum/AverageStart Max and Min at the first real value (loop from item 2) — never a fixed guess like 0 or 100
Linear searchChecks each item in order until a match or the end of the list; uses a flag variable (Found = TRUE/FALSE)
Bubble sortRepeatedly compares neighbours and swaps if in the wrong order; each pass bubbles the largest value to the end; stops early once a pass makes no swaps
⚠️ Why NOT Start Max/Min at 0 and 100.

Fixed guesses fail on data outside that range — e.g. all marks negative, or all marks above 100. Starting Max and Min at the first real value is always safe, whatever the data.

📘 Linear Search Worst Case

A class list of 30 names, with the match at position 30 (the very last spot): the search makes 30 comparisons — the worst case checks every single item.

7.5–7.6 Validation & test data

checking data
Validation vs verification
Validation = reasonable? Verification = copied correctly? Neither proves the data is actually true.

7.5 Validation vs Verification

ValidationVerification
Who/what checksThe PROGRAM, automaticallyThe PERSON (or system) doing the copying
Question asked"Is this a SENSIBLE answer?""Did I COPY it correctly?"
ExampleA mark of 150 fails — impossibleTyped 85 but meant 58 — both look sensible!

Six validation checks: range (0≤Mark≤100), length (password = 8 characters), type (must be a whole number), presence (field cannot be blank), format (matches a pattern, e.g. CUB9999), and check digit (an extra digit calculated from the others, e.g. ISBN/barcodes).

📘 Check Digits Catch 4 Error Types

Incorrect digit, transposition (two digits swapped), omitted/extra digit, and phonetic errors ("thirteen" instead of "thirty"). A check digit must be calculated from the other digits — a random extra digit wouldn't catch anything.

Two verification methods: double entry (typed twice, system compares both — used for "confirm password") and screen/visual check (data displayed on screen, user checks it against the original document — used for confirming an order before checkout).

⚠️ Trick Question.

'name@gnail.com' instead of 'name@gmail.com' — would validation catch it? No (it's still a valid email format). Would verification? Possibly (comparing against the original document could catch the copying error).

7.6 Test Data

TypeMeaningExample (Mark, 0–100)
NormalData the program SHOULD accept75
AbnormalData the program SHOULD reject−12, "eleven"
ExtremeThe largest/smallest value that IS accepted0, 100
BoundaryA pair straddling a limit — one accepted, one rejected−1 (reject), 0 (accept)
💡 Key Term — Boundary Data.

Always comes in a pair at each limit: one value that is accepted, and one that is rejected, right next to each other.

7.7–7.9 Trace tables & debugging

proving the algorithm works

7.7 Trace Tables

A trace table records a dry run step by step: one column per variable, plus one column for OUTPUT. Only write a new value in a column when it actually changes.

📘 Worked Example

An algorithm starts B ← 0, C ← 100, then updates B to the largest and C to the smallest value seen. With data 9, 7, 3, 12, 6, 4, 15, 2, 8, 5 it outputs 15, 2 — it finds the largest and smallest of 10 numbers.

⚠️ The Flaw in This Algorithm.

Because it starts B ← 0 and C ← 100, it gives the wrong answer for data that is all negative (largest wrong) or all above 100 (smallest wrong) — exactly the fixed-starting-value trap from 7.4.

7.8 Debugging Algorithms

Fixing the max/min algorithm to work for any data, in three attempts:

VersionStarting valuesProblem
1B ← 0, C ← 100Fails for negative numbers or numbers over 100
2B ← −1,000,000, C ← 1,000,000Better, but still fails outside that huge range
3 (best)B and C set to the first value inputAlways safe — loop then runs through the remaining 9 values only
⚠️ Off-by-One Error.

Version 3's loop is FOR Counter ← 1 TO 9 (not 10), because the first value was already read separately. Changing it back to TO 10 would try to read 11 numbers total for a 10-item list — a classic off-by-one error.

7.9 Writing Your Own Algorithms — Checklist

  • Understand the problem clearly
  • Break it into sub-problems (input, process, storage, output)
  • Decide how data is obtained, stored & displayed
  • Design the structure (a structure diagram)
  • Choose a flowchart or pseudocode
  • Construct it — use meaningful names and precise conditions
  • Test with normal, abnormal, extreme and boundary data + trace tables
  • Find errors → fix → repeat until correct
💡 Why Precision Matters.

Write Counter >= 10, not "Counter ten or over" — a computer needs an exact, unambiguous condition it can evaluate. Vague conditions can't be coded.

🔑 Key terms

Program development life cycle
The stages analysis, design, coding and testing, carried out in order to produce a working program.
Abstraction
Keeping only the details needed to solve a problem and removing unnecessary detail.
Decomposition
Breaking a problem down into smaller component parts: inputs, processes, outputs and storage.
Structure diagram
A design method showing a problem broken into a hierarchy of sub-systems.
Flowchart
A diagram that uses standard symbols to show the steps of an algorithm.
Pseudocode
Structured, language-independent text used to design and write an algorithm precisely.
Linear search
Checking each item in turn, from the start, until the target is found or the list ends.
Bubble sort
Repeatedly comparing adjacent items and swapping them if out of order until the list is sorted.
Totalling / counting
Totalling adds values into a running sum; counting adds 1 each time something happens.
Validation
An automatic check that input data is reasonable: range, length, type, presence, format and check digit.
Verification
A check that data has been entered correctly: visual check or double entry check.
Test data
Normal, abnormal, extreme (largest/smallest acceptable) and boundary (acceptable value plus the nearest rejected value).
Trace table
A table used to dry-run an algorithm, recording variables, outputs and user prompts at each step.
