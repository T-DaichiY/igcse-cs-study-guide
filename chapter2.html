2.1 How Data is Transmitted

Data packets, packet switching, serial/parallel and simplex/duplex methods, and USB

Data packets

Data sent over long distances is usually broken up into small units called data packets (or datagrams), typically around 64 KiB each. Splitting data into packets means each packet can be sent along a different route to its destination — useful if part of the network is busy or unavailable. The drawback is that the packets must be reassembled once they arrive.

Part of packetContains
HeaderOriginator's address (IP address of the sender)
Destination address (IP address of the receiver)
Packet number (sequence number, so packets can be put back in order)
PayloadThe actual data being carried (usually around 64 KiB)
TrailerA marker showing where the packet ends
An error-checking value — a cyclic redundancy check (CRC)
💡 Cyclic redundancy check (CRC): the sender counts all the 1-bits in the payload and stores this total as a hex value in the trailer. The receiver recalculates the same count once the packet arrives — if the two values match, no error occurred; if not, the packet is re-sent.
🧮 Worked example — CRC check on a payload

Payload received: 11110000 10000011 00110011 00111111 11111110 11100011

1Count every 1-bit across the whole payload.
2Convert that count to hexadecimal.
3Compare the hex value against the value stored in the trailer.
➜ This payload has 29 one-bits = 1D in hex. If the receiver's recalculated value ≠ 1D, the packet must be re-sent.

Packet switching

Packet switching sends each packet of a message independently from start to end. At each stage, a node containing a router examines a packet's destination address and decides which route it should take next — based partly on how congested each possible route currently is. Because different packets can take different routes, they can arrive out of order, so the destination device uses each packet's sequence number to reassemble them correctly.

Method: serial vs parallel transmission

Serial transmission sends data one bit at a time down a single wire — slower, but the bits stay synchronised, so it works well over long distances. Parallel transmission sends several bits (usually a byte) down several wires at once — faster, but over long distances the bits can arrive skewed (out of synchronisation), so it is best kept to short distances such as inside a computer.

💡 "Explain the suitability" questions: always give the method and a linked reason grounded in the scenario — distance, speed needed, and whether two-way communication is required. "Serial would be suitable because the printer is close by and only one wire is needed, reducing the risk of skewing" scores better than just naming "serial".

Universal serial bus (USB)

USB is a form of serial data transmission and is now the most common input/output port on computers, supporting both half-duplex and full-duplex communication. A standard USB cable has four wires: two (red, black) supply +5 V power, and two (white, green) carry the data.

📌 USB-C is a newer, 24-pin symmetrical connector (fits either way round), delivering up to 100 W of power and data rates up to 10 Gbps — enough for 4K video. It is backward compatible with USB 2.0/3.0 via an adaptor.

2.2 Checking for Errors

Why errors occur, and how parity checks, checksums, echo checks, check digits and ARQ detect them

Why errors must be checked

Data can be corrupted, lost, or even gained during transmission because of interference on a cable, problems during packet switching, or skewing during parallel transmission. Unlike a human reading scrambled text, a computer cannot guess the intended meaning of corrupted data — it needs the data to be exactly correct, or explicitly flagged as an error.

💡 A human can still read "Cmabridge Uinervtisy" because the mind reads a word as a whole. A computer cannot do this — it needs error-checking methods to catch corrupted data.

Parity checks

A parity check is based on the number of 1-bits in a byte. Even parity means the byte should contain an even number of 1-bits; odd parity means an odd number. One bit (usually the left-most) is reserved as the parity bit, set so the byte matches whichever protocol (odd/even) sender and receiver agreed in advance.

🧮 Worked example — detecting an error with even parity
Parity bitBits 2–8Total 1-bits
Byte sent010111004 (even — correct)
Byte received010011003 (odd — error!)
➜ Even parity was agreed, but the received byte has an odd count of 1-bits — the receiver flags a transmission error.
⚠️ Parity's blind spot: if exactly two bits in a byte both flip, the parity count stays correct and the error goes completely undetected. This is why parity alone is not enough on its own — other methods such as checksum are used alongside it.
💡 Parity block/parity byte: sending a block of bytes together with an extra parity byte (built from the vertical/column parity of the block) lets a receiver locate the exact corrupted bit — the intersection of the row with wrong (horizontal) parity and the column with wrong (vertical) parity.

Checksum

StepProcess
1Before sending, a checksum is calculated from the data block using an agreed algorithm.
2The checksum is transmitted along with the block of data.
3The receiver recalculates the checksum from the data it received, using the same algorithm.
4The two checksums are compared.
5If they match, no error occurred; otherwise the block is re-sent.

Echo check

With an echo check, the received data is sent straight back to the sender, who compares it with the original. If the two match, transmission was error-free.

⚠️ Echo check is not very reliable: if the two sets of data differ, it is impossible to tell whether the error happened on the way out, or on the way back.

Check digits

A check digit is a data-entry check, not a transmission check — it catches errors made when a human types a number or a scanner misreads a barcode (incorrect digit, transposition, omitted/extra digit, phonetic error). Used in ISBNs and other product codes.

🧮 Worked example — generating an ISBN-13 check digit

Twelve-digit number: 9 7 8 0 3 4 0 9 8 3 8 2

1Add all odd-position digits: 9+8+3+0+8+8 = 36.
2Add all even-position digits, multiply by 3: 3×(7+0+4+9+3+2) = 3×25 = 75.
3Add the two totals and divide by 10: (36+75)÷10 = 111÷10 = 11 remainder 1.
4If the remainder isn't 0, subtract it from 10: 10−1 = 9.
➜ Full ISBN-13: 9 7 8 0 3 4 0 9 8 3 8 2 9
🧮 Worked example — modulo-11 check digit

Seven-digit number: 4 1 5 6 7 1 0, weightings 8 down to 2.

1Multiply each digit by its weighting and total: (8×4)+(7×1)+(6×5)+(5×6)+(4×7)+(3×1)+(2×0) = 130.
2Divide by 11: 130÷11 = 11 remainder 9.
3Subtract the remainder from 11: 11−9 = 2 (if the remainder were 10, the check digit is "X").
➜ Full code: 4 1 5 6 7 1 0 2
📌 You don't need to memorise these algorithms — in the exam the steps are given to you. What matters is applying the given algorithm accurately, keeping careful track of odd/even positions.

Automatic Repeat reQuest (ARQ)

StepWhat happens
1The receiver checks the data using an error-detection code (typically a CRC).
2No error found → a positive acknowledgement is sent back.
3Error found → a negative acknowledgement is sent, requesting re-transmission.
4The sender waits a set time (the timeout) for any acknowledgement.
5No acknowledgement at all within the timeout → the sender automatically re-sends the data.
💡 A complete ARQ answer covers all three parts: the error-detection code, positive/negative acknowledgements, and the timeout — an answer that only mentions resending after an error, and never the timeout case, is incomplete.

2.3 Keeping Data Secure

The purpose of encryption, and symmetric vs asymmetric encryption

The purpose of encryption

Data sent over any public network risks being intercepted by an eavesdropper. Encryption cannot stop the data being intercepted — but it can stop the intercepted data making any sense to whoever intercepts it.

⚠️ Common exam mistake (June 2025 examiner report): don't say encryption makes data "unreadable" — it doesn't. The data can still be looked at; encryption makes it meaningless to anyone without the correct decryption key. Use "meaningless" or "scrambled", not "unreadable".
StageWhat happens
1. PlaintextThe original, readable message, before encryption
2. EncryptionPlaintext is processed by an encryption algorithm using an encryption key, producing ciphertext
3. TransmissionThe ciphertext travels across the (possibly insecure) network
4. DecryptionCiphertext is processed by a decryption algorithm using a decryption key, restoring the plaintext

Symmetric encryption

Symmetric encryption uses the same key to both encrypt and decrypt.

🧮 Worked example — a simple shift-substitution key

Encryption key 4291362856 shifts each letter forward by the matching digit.

PlaintextCOMPUTER
Key digit42913628
CiphertextGQVQXZGZ
➜ "COMPUTER" → "GQVQXZGZ". To decrypt, the receiver shifts each ciphertext letter backwards by the same key digits.
⚠️ Real systems use 256-bit keys, not 10 digits — but the biggest risk isn't brute-force cracking, it's keeping the shared key secret while it travels to both sender and receiver. That transmission of the key itself can be intercepted.

Asymmetric encryption

Asymmetric encryption uses two mathematically linked keys that cannot be derived from each other: a public key (shared with everyone) and a private key (kept secret by its owner).

🧮 Worked example — Tom sends Jane a confidential document
1Jane generates a matching public/private key pair.
2Jane sends Tom her public key.
3Tom encrypts the document with Jane's public key and sends it back.
4Jane decrypts it using her matching private key — no other key will work.
➜ Jane's private key never leaves her computer, so it can never be intercepted in transit.
Symmetric encryptionAsymmetric encryption
Number of keysOne (shared)Two (public + private)
Same key encrypts/decrypts?YesNo — public key encrypts, private key decrypts
Main weaknessShared key must be sent secretly — can be interceptedNo shared secret is ever transmitted
SpeedGenerally fasterGenerally more computationally demanding
📌 Why asymmetric is more secure: because the private key is never transmitted anywhere, there's no shared secret in transit for an eavesdropper to intercept — unlike symmetric encryption's single shared key.

🔑 Key terms

Data packet
Small unit (~64 KiB) of data sent over a network, reassembled at the destination.
Packet header / payload / trailer
Addresses + sequence no. / the actual data / end marker + CRC.
Router
Examines a packet's header and decides its next route.
Packet switching
Message split into packets, sent independently, reassembled at the end.
Simplex / Half- / Full-duplex
One direction / both, not at once / both, at once.
Serial / Parallel
One bit, one wire, in order / several bits, several wires, at once.
Skewed data
Bits arrive out of sync — a risk in parallel transmission.
USB
Industry-standard serial interface; auto-detects devices and loads drivers.
Parity check / bit
Extra bit set so a byte's 1-count matches an agreed odd/even protocol.
Checksum
Value calculated from a data block, resent and recompared to check for corruption.
Echo check
Received data is sent straight back to the sender to compare.
Check digit
Extra digit that catches data-entry errors, e.g. in an ISBN.
ARQ
Uses acknowledgements + a timeout to trigger automatic re-transmission.
Plaintext / Ciphertext
Original readable message / scrambled result after encryption.
Symmetric / Asymmetric encryption
One shared key both ways / public key encrypts, private key decrypts.

📌 Exam tips

Encryption makes data meaningless, not unreadable — a hacker can still see the characters, they just can't understand them.

When explaining the suitability of a transmission method, name both the channel method (serial/parallel) and the direction (simplex/half-/full-duplex), linked to the scenario's distance and speed needs.

For a parity-check question, state the specific protocol (odd or even) that was agreed — a generic "a parity bit is added" answer loses marks.
